# 残りテスト実装 議事録

日付: 2026-10-21

`FieldSyncLoggerViewModel` のテストは実装済み。ここから下は、その後に決めた範囲。

## テストを実装するクラスと優先度

今回書くのは JVM の単体テストだけである。置き場所は `app/src/test`。計測テストは使わない。

優先度は次の順。上から実装する。

1. `FieldSyncLoggerRepositoryImpl`
2. `SyncWorker`
3. `SaveLoggerUseCase`、`LoadReportsUseCase`、`SyncUnsyncedReportsUseCase`

1と2に、保存・同期・`Result` の分岐がある。3つの UseCase は Repository へ渡すだけなので、同じ引数で対応メソッドを1回呼ぶことを見る。成否の分岐は UseCase には無い。

各クラスのテストケースの一覧は、まだ決めていない。クラスの実装に入るときに見る。

## テストの実行場所

`saveLogger` の登録内容も JVM で見る。登録内容は、Repository のテストで、偽物が受け取った `WorkRequest` を見る。

WorkManager がネットワーク接続まで待ってから作業を動かすことは、今回見ない。

## 登録口

登録は `enqueue` のままにする。`enqueueUniqueWork` へは変えない。

`saveLogger` は、未同期での `insert` と、`SyncWorker`・`NetworkType.CONNECTED` の `OneTimeWorkRequest` の組み立てを残す。組み立て済みの `WorkRequest` を、コンストラクタで受け取った登録口へ渡す。本番の登録口だけが `WorkManager.enqueue` を呼ぶ。`insert` より前には登録しない。Repository のコンストラクタから `Context` を外す。`saveLogger(content: String)` と 3つの UseCase の引数は変えない。

置き場所は次のとおり。実装済み。

- `worker/SyncWorkEnqueuer.kt`。`WorkRequest` を1つ受ける interface
- `worker/WorkManagerSyncWorkEnqueuer.kt`。本番の実装クラス
- `di/SyncWorkEnqueuerModule.kt`。`provideWorkManager`
- `di/FieldSyncLoggerModule.kt`。`bindSyncWorkEnqueuer`

`syncUnsyncedReports` の `for` は、Android Studio の lint 対応で分解代入に変えた。ログに出す値は `content` のままである。

## SyncWorker の結果

- 正常完了は `Result.success()`
- `IOException` は `Result.retry()`
- `CancellationException` は再スローする。`Result.failure()` にも `Result.retry()` にもしない
- それ以外の `Exception` は `Result.failure()`

`CancellationException` の捕捉は `catch (e: Exception)` より前にする。`IOException` との前後は、この例外の振り分けには影響しない。

この再スローは、実装済み。

## 対象外

- `MainActivity`
- 計測テスト
- `ReportDao`

`ReportDao` は、クラス確認の段階でレビュー側が対象に足すよう指摘した。その段階ではテストケースの過不足を決めないこととしたため、実装対象には入れていなかった。

`ReportDao` のテストは Room の SQL を実行する。JVM の単体テストでは SQLite を実行できず、計測テストになる。今回は計測テストを使わない。そのため `ReportDao` は今回の対象外にする。計測テストを行う段で改めて対象にする。

## この会話では決めなかったこと

各クラスのテストケースの過不足は、クラスの範囲を確認した段階では決めていない。テストケースは、そのクラスの実装に入ってから見る。
